# Process-local run history

`integration::freshness::RunHistory` is bounded in-memory history with compare-and-swap generations. It neither persists across restart nor authenticates evidence. The pointer called `current` is the latest completed local attempt, including errors/cancellation/BLOCK; it is never an eligibility or approval pointer.

A prepared producer exposes immutable WorkKey. Its SHA256 covers full RunBinding (repository/task/worktree/required IDs, candidate/base/merge-group, source/baseline digests), producer/analyzer versions, initial frozen coverage, fixed engine/profile IDs, the complete frozen SourceSnapshot including parsing limits/source inventory/bytes, required identities and exact ProtectedMapping contract/entries. Hashing streams serialized borrowed inputs after producer admission; reordering caller mapping vectors conservatively creates different work. Policy revision/content changes for the same candidate therefore cannot reuse the old key.

Run ID and started-at timestamp deliberately identify an attempt rather than work: retrying the same work has the same work key but must supply a new run ID. They remain immutable inside the prepared attempt and completion envelope. Existing producer validation still checks real candidate objects; this store adds no clean queue-tree, identity, approval, expiry or revocation authority. Tasks3.5 and3.7 are unchanged.

`register(prepared, expected_generation)` consumes frozen work, rejects reused run IDs globally and stale generations, then advances that target and immediately clears its old current pointer. Target includes repository, task, worktree and canonical requirement set. Different requirement sets have distinct targets even at the same candidate. The returned RegisteredRun can execute the existing cooperative runtime; execution returns an opaque Completion with the private store registration receipt and immutable output. There is no constructor/deserializer/raw-envelope import for Completion. A caller may clone/edit a ProducedRun for other purposes, but cannot append or relabel that clone as tracked work.

`append(&completion)` validates store identity/registration and the actual GE/domain bundle, records append-only history and permits identical typed replay. `publish(&completion)` requires an appended record and the still-current generation. Late old-policy/candidate completion may append to history but cannot publish. Receipt identity is unique per store, so a completion from another process-local store cannot be imported even with the same run ID/work. Store mutation requires exclusive `&mut` access; a host sharing the store among threads must synchronize it, while registered work can execute independently on real threads.

Limits are256 registrations per store,16MiB serialized bytes per retained bundle,64MiB combined conservative registration/output admission. Registration cost reserves copied target/key/run strings before mutation; capacity errors leave generation/pointer unchanged. No eviction/reuse or rollover is implicit. These are bounded admission counters, not an allocator/RSS or crash-durability guarantee. Source/producer work has its own existing budgets.

Validation includes actual two-requirement worker threads with one paused after source progress, same-candidate protected-policy change, out-of-order completion, cancelled retry clearing old success, duplicate ID/stale CAS, foreign-store receipt rejection, every exposed binding/source-policy dimension and a full registration-capacity boundary. Compile-fail examples prohibit private receipt construction and raw ProducedRun append. See tests/concurrent_runs.rs. No filesystem publisher, current-file marker, provider or privilege operation is added.
